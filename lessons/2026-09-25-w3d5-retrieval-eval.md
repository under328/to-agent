## 任务卡

### T1 · golden set（15min，评测的灵魂）

```jsonl
{"q": "Vue 3 响应式基于什么实现", "expectSource": "vue-notes.md", "expectHeading": "响应式系统"}
{"q": "为什么我的提交没有被 CI 执行", "expectSource": "ci-notes.md", "expectHeading": "触发规则"}
```

**出题原则**：①从**真实文档**出题（拿你自己的笔记/项目文档入库），别编——编的问题都是「友好分布」，测不出真实短板；②10 问覆盖四种类型：直问（术语原词）、换说法（同义改写）、口语化（怎么东问西问）、负面提问（库里没有答案的问题，期望=拒答）。

### T2 · 指标实现（10min）

```ts
// hit@k：期望 chunk 出现在 top-k 里记 1 分
// MRR（平均倒数排名）：期望 chunk 排第 m 位记 1/m——反映「排得靠不靠前」
const mrr = cases.reduce((s, c) => s + (c.rank ? 1 / c.rank : 0), 0) / cases.length
```

**决策点**：为什么 hit@k 起步就够——它确定性、可解释、零成本；MRR 补充「排名质量」。NDCG、recall@k 那些等有排序优化需求（W4 的 rerank）再上，**指标跟着需求长，不提前堆**。

### T3 · 控制变量实验（15min）

固定其他参数，一次改一个：

| 轮次 | 变量 | 取值 |
| --- | --- | --- |
| 基线 | maxChunkChars=500, overlap=0.15, k=5 | 记录 hit@1/3/5 |
| 实验A | maxChunkChars=300 | 重跑，对比 |
| 实验B | maxChunkChars=800 | 重跑，对比 |

每轮结果追加进 `eval/SCORES.md`（作品 1 的老规矩）。**预期**：300 可能切碎语义、800 可能稀释信号——但你的文档上真实数字说了算，这就是「我有数据」和「我猜的」的区别。

### T4 · 校准拒答阈值（5min）

用 golden set 里的「负面问题」组：调 `MIN_SCORE` 使「该拒的拒、该答的答」。把最终值和依据写进 journal——这个数字从此有了出处。

## 关键决策与原理

1. **检索评测先于生成评测**：RAG 答错，八成是检索没命中（垃圾进垃圾出），生成只背小半锅——先测检索，定位问题才有层次；
2. **换说法与口语化问题是最有价值的用例**：直问谁都能过，真实用户全是「换个说法问」——这两类问题的 hit@3 才是检索内核的真实水平；
3. **负面问题进评测集**：没有「库里没有」的用例，拒答阈值永远没人校验——评测集决定了一个系统的性格，包含失败路径才是完整的评测；
4. **每轮实验记录完整参数快照**：三个月后回看 SCORES.md，只有「分数变了」没有「当时参数是什么」，等于白测。

## 自测题（答完翻底部）

1. RAG 答错了，为什么先查检索再查生成？
2. hit@1、hit@3、hit@5 分别在测什么？MRR 补充了什么信息？
3. 为什么 golden set 必须用真实文档出题？
4. 「负面问题」在评测集里的作用是什么？
5. 控制变量实验的记录纪律是什么？

---

## 答案与解析

1. 检索是输入质量的守门员：命中错了，生成模型再强也是基于错误资料作答；先确认「该找到的找到了」，才能把问题归因到生成环节；
2. hit@k 测「期望结果进没进前 k」——hit@1 测排序头部质量（用户第一眼），hit@3/5 测召回兜底；MRR 用倒数排名补充「进了 top-k 但排多靠后」的信息；
3. 编造的问题措辞规范、词汇分布友好，会把检索短板（措辞差异、口语化）全部藏住；真实文档出的问题才暴露真实分布下的失败模式；
4. 它们是拒答机制唯一的校验来源：没有「库中无答案」的用例，就无法测量误拒率与漏拒率，阈值永远只能拍脑袋；
5. 每轮只改一个参数 + 记录完整参数快照 + 分数追加进 SCORES.md——让任何一次分数变化都可归因、可复现。
