# W4-D2 ｜ rerank 精排：top-20 → top-5 的最后一道关卡

> **前置**：D1 混合检索已就绪。
> **今日一句话**：召回管「找全」，精排管「排准」——rerank 是检索管线里性价比最玄学、也最见工程判断的一环。

## 任务卡

### T1 · 为什么两阶段（10min）

类比招聘：**初筛（检索）要宁滥勿缺**——20 份简历里不能漏掉对的人；**终面（rerank）要精挑细选**——只把最合适的 5 个送进下一轮。两个目标冲突，所以分成两个阶段、用两种工具：检索器快而糙（毫秒级、全库扫），reranker 慢而准（只看 20 个候选，逐个细读）。

### T2 · listwise 重排实现（20min）

```ts
const rerankSchema = z.object({
  items: z.array(z.object({
    index: z.number(),              // 候选编号（对应输入顺序）
    relevance: z.number().min(0).max(2), // 0=无关 1=部分相关 2=直接回答了问题
    reason: z.string(),
  })),
})

export async function rerank(question: string, candidates: Chunk[], k = 5) {
  const listing = candidates.map((c, i) => `[${i}] ${c.heading}：${c.content.slice(0, 200)}`).join('\n')
  const { object } = await generateObject({
    model: llm(process.env.LLM_MODEL_FLASH!),  // 精排用 flash 档：量大、任务简单
    schema: rerankSchema,
    temperature: 0,
    prompt: `问题：${question}\n\n候选片段：\n${listing}\n\n给每个候选的相关度打分（0/1/2）。`,
  })
  return object.items
    .filter(i => i.relevance >= 1)
    .sort((a, b) => b.relevance - a.relevance)
    .slice(0, k)
    .map(i => ({ ...candidates[i.index], rerankScore: i.relevance }))
}
```

**决策点（listwise vs pointwise）**：逐条打分（pointwise）要 20 次调用，且打分没有参照系、分数漂移大；列表式（listwise）一次调用、候选之间可互相对比（「谁更能回答这个问题」），又便宜又稳。**能用 listwise 就不用 pointwise**。

### T3 · 管道集成（10min）

```ts
export async function search2(query: string, { k = 5, useRerank = false } = {}) {
  const candidates = await hybridSearch(query, { k: useRerank ? 20 : k })  // 重排时先宽召回
  return useRerank ? rerank(query, candidates, k) : candidates
}
```

注意召回宽度跟着变：开 rerank 就先取 20 再精选 5，不开就直接 5——**rerank 的前提是「宽进严出」**，20 进 5 才有精选空间。

### T4 · 数据说话（10min）

跑三轮评测：关 rerank / 开 rerank，各记 hit@1、hit@3；同时把 rerank 的单次成本与延迟写进日志。三种可能结论都正常：①头部排序明显变好（hit@1 ↑）；②打平（说明你的检索器已经够好，rerank 暂时不值）；③反而变差（flash 档判断力不够或 prompt 不行）。**结论无论哪个都写进 SCORES.md**——「我们测过、rerank 暂不开启」是一个完整的工程决策，比无脑开着强。

## 关键决策与原理

1. **rerank 是「按需开启」的奢侈品**：它给每个查询加一次 LLM 调用（约 1 万 input tokens、1~2s 延迟）——答案质量敏感的路径开，闲聊式检索不开；
2. **重排模型降档**：精排任务输入输出都结构化、判断面窄，flash 档足够；旗舰档留给生成。这是 W2-D3 模型路由思想的局部应用；
3. **宽进严出**：rerank 只在「候选里确实有答案」时有价值，召回宽度不足时 rerank 无米下锅——20 进 5 是常用的起步配比；
4. **judge 与 rerank 是近亲**：昨天评测的 LLM-as-judge 和今天的 rerank 本质都是「LLM 做相关性判断」，rubric 设计经验直接迁移（明确的 0/1/2 档位定义）。

## 自测题（答完翻底部）

1. 检索和 rerank 的目标差异是什么？为什么必须分两阶段？
2. listwise 相比 pointwise 的两个优势？
3. 为什么开 rerank 时召回宽度要放大（20 而不是 5）？
4. rerank 评测打平，正确的工程结论是什么？
5. rerank 的成本大头在输入还是输出？为什么？

---

## 答案与解析

1. 检索求高召回（不漏，快而糙）；rerank 求高精度（排准，慢而细）。单一模型同时优化两个冲突目标效率低，两阶段各司其职；
2. 一次调用处理全部候选（省成本、低延迟）；候选在同一个上下文里互相对比，相关性判断有参照系，分数更稳；
3. rerank 的价值来自「从更多候选里精选」；召回宽度=5 时 rerank 只能重排这 5 个，排错也无米可换——宽进严出才有精选的余地；
4. 「当前检索器已够好，暂不开启 rerank」——附带成本数据一起记录，作为完整工程决策存档；将来文档量/问题分布变化时重启评测；
5. 输入。20 个候选片段（约 1 万 token） vs 输出（结构化评分几百 token），且输入按 input 单价计费——所以候选片段要截断（如 200 字）控制成本。
