## 任务卡

### T1 · 内核集成方式（10min，先决策后动手）

```bash
cd projects/docqa
pnpm add "file:../knowledge"
```

**决策点**：三种集成方案的取舍——①复制代码（简单但双份维护，否）；②npm 发私有包（过重，否）；③`file:` 协议本地依赖（pnpm 会做符号链接，knowledge 改动即时生效，且保留了「内核是独立包」的边界感）。选 ③。将来作品 2 接内核，还是这一招——**今天的决策在 W5 会再赚一次**。

### T2 · 上传与入库 API（20min）

```ts
// app/api/ingest/route.ts
export async function POST(req: Request) {
  const form = await req.formData()
  const file = form.get('file') as File
  if (!file.name.endsWith('.md')) return Response.json({ error: '仅支持 .md' }, { status: 400 })
  const md = await file.text()
  const chunks = chunkMarkdown(md, file.name)          // W3-D2
  await ingestChunks(chunks)                            // 向量 + FTS 双写（事务）
  return Response.json({ chunks: chunks.length })
}
```

**决策点**：v1 只收 `.md` 并明确报错——格式支持是产品面，每多一种格式就多一类切块边界问题；先把 .md 路径打穿，PDF/DOCX 是后续版本的事。

## 关键决策与原理

1. **内核与应用分离的回报期到了**：knowledge 包不含任何 UI 依赖、接口早已冻结（W3-D3），今天只写「壳」；如果当初把切块/检索写在 CLI 里，今天就是一次重写——分层不是教条，是给未来的自己留门；
2. **上传即入库的失败面**：文件编码（GBK 的中文 md！）、超大文件、空文件都要在 ingest 入口拦住并给出人话错误——上传是用户接触产品的第一秒，报错体验决定去留；
3. **引用卡片是 RAG 应用的灵魂 UI**：用户点开引用核对原文的那一刻，信任建立；卡片信息层级：来源 > 标题 > 片段 > 分数，分数放最后（用户不关心你的余弦值，关心「出处硬不硬」）；
4. **本地 SQLite 的舒适区与边界**：本地开发一切丝滑，但 Vercel 这类 serverless 平台文件系统是临时只读的——**明天的部署课会正面处理这个问题**（三条路线），今天先把本地链路打穿。

## 自测题（答完翻底部）

1. `file:` 协议依赖相比复制代码的优势？相比 npm 私有包的取舍？
2. 为什么 v1 只支持 .md 上传？
3. 引用卡片的信息层级怎么排？为什么分数放最后？
4. 「显式简化」与「默认疏忽」的区别是什么？
5. 本地 SQLite 应用直接部署到 Vercel 会遇到什么问题？

---

## 答案与解析

1. `file:` 是符号链接式本地依赖，内核改动即时生效且保持独立包边界；复制代码会分叉维护；npm 私有包要搭版本发布流程，当前阶段过重——等内核稳定、多项目消费时再升级；
2. 每种格式都带来新的切块边界问题（PDF 分页/双栏、DOCX 样式），单格式先把「上传→入库→问答」全链路的工程质量做透，再扩格式；
3. 来源 > 标题 > 原文片段 > 分数；用户核对引用要的是「出处可不可信」，相似度分数是工程内部指标，对用户是噪声；
4. 显式简化写进 README/Roadmap、有明确的演进方案，是知情的产品决策；默认疏忽是没想过，将来以事故形式重新出现；
5. serverless 函数的文件系统是临时的（实例间不共享、可能只读），SQLite 的写入会丢失——需要明天讲的三条路线：打包只读库 / 云 SQLite（Turso）/ 持久卷自托管。
