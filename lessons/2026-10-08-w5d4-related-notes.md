# W5-D4 ｜ 相关笔记关联：入库即向量化，「可能相关」的谦逊设计

> **前置**：D3 整理管线可用。
> **今日一句话**：让相关笔记自动浮出来——但用「可能相关」的措辞，因为模型不该为「确定相关」背书。

## 今日验收

- [ ] 新笔记入库 → 整理完成后自动向量化入库（embedding 状态机复用 embed_status）
- [ ] 笔记详情页展示「相关笔记」top-3（余弦 ≥ 阈值才展示，阈值可配置）
- [ ] 反向视图：某笔记被哪些笔记关联过（被引用清单）
- [ ] 相似度分数不展示给用户（内部指标），UI 措辞为「可能相关」

## 任务卡

### T1 · 增量向量化（15min）

```ts
// 整理完成后（D3 的 enrichNote 尾部）追加：
async function vectorizeNote(id: number) {
  const note = getNote(id)
  const { embedding } = await embed({ model: embedModel, value: `${note.title}\n${note.content}` })
  upsertNoteVec(id, embedding)   // 有则更新、无则插入——笔记可编辑，向量要跟着更新
}
```

**决策点：向量放独立表还是 notes 表加列？** 沿用 knowledge 内核模式（独立 vec 表 + rowid 映射）——向量列是二进制大数据，混在业务表里拖累全表扫描；且「换 embedding 模型只重建向量表」的路径保持畅通。**业务表保持瘦，检索物化数据独立**。

### T2 · 相关推荐（15min）

```ts
export function relatedNotes(id: number, { k = 3, minScore = 0.5 } = {}) {
  const self = getVec(id)
  const hits = searchByVec(self, k + 1)          // 多取 1 个（会包含自己）
  return hits.filter(h => h.id !== id && h.score >= minScore).slice(0, k)
}
```

**决策点：阈值 0.5 的含义**——余弦低于阈值的「弱相关」是噪音主要来源（向量空间里八竿子打不着的两段文字也有 0.3~0.4 的基础相似度）。阈值是产品参数：宁缺毋滥（0.5 起步）比「总有推荐」更重要，**空状态「暂无相关笔记」是合法 UI**。

### T3 · 双向关系与 UI 措辞（15min）

- 正向：详情页「可能相关的笔记」卡片（标题 + 摘要 + 一键跳转）；
- 反向：「哪些笔记提到了它」——查询上就是反向的 relatedNotes（同一套函数换个方向），但认知价值不同：正向是「顺藤摸瓜」，反向是「这条知识被谁用上了」；
- **措辞纪律**：所有 AI 生成的关系都用「可能相关」而不是「相关笔记」——推荐错误时用户的容忍度完全不同。**AI 功能的谦逊措辞是产品可靠性的一部分**，面试聊「AI 功能的产品设计」时这是好例子。

### T4 · 一致性保障（10min）

三个写入口都要保证向量与笔记一致：新建（整理后向量化）、编辑（重新向量化，upsert 语义已覆盖）、删除（向量与 FTS 同步删除——W4-D1 双写的对称操作）。写一个一致性自检脚本：`pnpm check-consistency` 比对三方行数与孤儿向量。

## 关键决策与原理

1. **增量而非全量**：只向量化新增/变更的笔记——复用 W4 上传入库的模式；全量重算既浪费钱又慢，增量是写密集型产品的必然选择；
2. **弱相关是噪音之源**：余弦有「基础相似度地板」（任何中文文本对都在 0.3~0.4），阈值必须切在地板之上——这个数字应该来自你自己的观察而不是论文；
3. **推荐 vs 断言的产品措辞**：「可能相关」给了用户忽略权，也给了系统出错空间——AI 输出的 UI 呈现要按其置信水平定级，这是 AI 产品设计的通用原则；
4. **一致性自检脚本**：多存储（业务表/向量表/FTS 表）的系统必然出现漂移，一个 10 分钟写的对账脚本，是「数据修好了但没人知道坏了」的解药。

## 进阶挑战（选做）

- 「相关笔记」支持负反馈：点「不相关」记录下来（将来是 rerank/推荐评测的负样本来源）；
- 相似度分布统计：跑 50 条笔记的相关推荐，画一下分数分布直方图（验证 0.5 阈值落在哪个分位）。

## 自测题（答完翻底部）

1. 为什么向量数据放独立表而不是 notes 表加一列？
2. 余弦相似度的「地板效应」是什么？对阈值设置意味着什么？
3. 「可能相关」的措辞为什么是产品问题而不是文案问题？
4. 哪三个写入口需要维护向量一致性？
5. 一致性自检脚本防的是什么病？

---

## 答案与解析

1. 向量是大二进制列会拖累业务表读写；独立表让「换 embedding 模型→重建向量表」不动业务数据——物化数据与业务数据分离的老原则；
2. 任意两段文本都有非零的基础相似度（通常 0.3~0.4），低于阈值的推荐全是噪音；阈值必须切在地板之上，且来自自家数据分布观察；
3. 措辞设定了用户预期与出错容忍度：「可能相关」错了可忽略，「相关」错了伤信任——AI 置信水平要显式传导到 UI 语义；
4. 新建（整理后向量化）、编辑（重新向量化 upsert）、删除（向量与 FTS 同步清理）；
5. 多存储漂移：业务表、向量表、FTS 表各自增删改后出现孤儿行/缺行，表现为「搜不到明明存在的笔记」——对账脚本让漂移可见可修。
