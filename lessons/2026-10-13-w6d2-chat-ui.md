## 任务卡

### T1 · 单轮 + 推荐追问的范围决策（10min，先决策后动手）

**为什么 v1 不做多轮对话**：多轮意味着上下文管理（历史裁剪/摘要压缩，W2 学过）、成本随轮数膨胀、以及「对话状态」的产品复杂度。而笔记问答的真实场景是「一问一答就够」+「顺着再问一个」——后者用**推荐追问**（检索完成后让 flash 基于资料生成 3 个 follow-up 问题）覆盖 80% 需求，成本只有多轮的零头。

**升级条件写进注释**：「接着上面说的」类需求在一周狗粮日志中出现 ≥3 次 → 上多轮（届时复用 W2-D2 的历史裁剪）。

```ts
// 检索完成后追加一次调用（复用整理管线的合批思路）：
const followups = await generateObject({
  model: flash, temperature: 0.7,   // 追问要一点发散
  schema: z.object({ questions: z.array(z.string()).max(3) }),
  prompt: `资料：${context}\n用户问题：${q}\n生成 3 个用户可能接着问的问题。`,
})
```

### T2 · 引用跳转与片段高亮（20min，今天最值钱的交互）

```
/notes/123?hl=1204,1580     ← URL 带 offset（W3-D2 切块时存下的坐标系）
```

- 详情页解析 `hl` 参数 → 对应字符区间 `scrollIntoView({ block: 'center' })` + 高亮动画（CSS transition 渐入渐出 2s 后淡出）；
- 决策点：为什么用 **URL 参数**而不是组件内 state——链接可分享给未来的自己/朋友、刷新不丢、详情页保持「无外部依赖的纯函数」（参数进，视图出）。

### T3 · 流式与状态机（10min）

作品 1 的三态状态机 + reader 直接搬，新增一种输入形态：问答框在移动端要「键盘弹起不被遮挡」（`visualViewport` 或简单的 `scroll-margin` 兜底）。

### T4 · 移动端走查（10min）

手机走一遍主流程：录入 → 列表 → 详情 → 问答 → 引用跳转。重点：触控目标 ≥44px、引用卡片全宽可点、键盘遮挡。**你的狗粮 70% 发生在手机上**——这里磨叽一秒，狗粮日志就多一条抱怨。

## 关键决策与原理

1. **范围决策的「覆盖 80% 成本的 20%」判断**：推荐追问用一次 flash 调用模拟了多轮对话的核心体验——**先用量产方案验证需求，再决定要不要重武器**；
2. **URL 即状态**：高亮、筛选、页码这类「可分享的视图状态」放 URL，组件状态只留「瞬时的交互态」——这条习惯会让你未来的每个功能都自带可分享性；
3. **移动端不是适配项而是主场景**：录入行为发生在「不在电脑前」的时刻（通勤/会议/厕所），狗粮数据会证明这一点——设计时就把手机当第一公民；
4. **本地历史的价值**：问答历史是「我的知识足迹」，也是 D5 评测出题的素材库——存下来，别让每次回答蒸发。

## 进阶挑战（选做）

- 问答页支持「只在这些标签里找」的过滤器（复用 D1 的标签过滤）；
- 历史问答支持「重新生成」（模型/参数更新后的对比，很直观）。

---

## 答案与解析

1. 多轮：全量历史进上下文，成本随轮数线性涨，还要管裁剪/摘要；推荐追问：一次 flash 调用（几分钱）给出「下一步问什么」，覆盖主要心智——先低成本模拟，数据证明需求再升级；
2. URL 状态可分享、可刷新、可收藏，详情页退化为「纯函数」（参数→视图），测试与复用都更容易；组件 state 一刷新就蒸发；
3. 把「什么时候该做重活」变成可判定的客观条件（日志出现 ≥3 次），防止两类错误：过早优化与永远不做——决策留痕，未来自己不用重新吵一遍；
4. 移动端问题（键盘遮挡/触控目标）在记忆新鲜时修复成本最低；拖到周会后，狗粮日志里已经堆了一堆抱怨，返工面变大；
5. 它是 D5 评测的出题素材库（真实问题分布）+ 未来做检索优化的 A/B 数据源（同问题重新生成的答案对比）。
