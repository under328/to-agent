# W3-D2 ｜ 切块器：把文档切成「检索友好」的块

> **前置**：D1 向量库可存可查。
> **今日一句话**：切块（chunking）决定检索上限——切块失当，后面全在给坏输入打工。

## 今日验收

- [ ] `src/chunker.ts`：混合策略切块器——先按 Markdown 标题/段落切语义块，超长块再滑窗二次切
- [ ] 三个参数可配置：`maxChunkChars`（默认 500）、`overlap`（默认 0.15）、最小块合并阈值
- [ ] 每个块携带元数据：`{ source, heading, startOffset, endOffset, content }`
- [ ] 完整性测试：对样例 Markdown 切块，拼接所有块内容去 overlap 后与原文一致（不丢字）

## 任务卡

### T1 · 为什么切块（5min，想清楚再写代码）

- embedding 模型有输入上限，且**块越长，语义越稀释**（一个 3000 字的块的向量 ≈ 一锅粥）；
- 检索粒度 = 块：块太大→命中不精准（命中的大块里大半是废话，浪费上下文预算）；块太小→语义破碎（「它」指代丢失，单块不可理解）；
- 中文经验值：**300~800 字/块**，重叠（overlap）10%~20% 防止句子被切断后两边都不可用。

### T2 · 语义边界优先（15min）

```ts
// 策略：Markdown 按 ## 标题切段 → 段落内超长再滑窗
export function chunkMarkdown(md: string, source: string, opts: ChunkOptions = {}): Chunk[] {
  const sections = splitByHeadings(md)          // [{ heading, body, startOffset }]
  const chunks: Chunk[] = []
  for (const s of sections) {
    if (s.body.length <= (opts.maxChunkChars ?? 500)) {
      chunks.push(makeChunk(s, source))
    } else {
      chunks.push(...slidingWindow(s, opts))    // 二次滑窗，继承 heading 元数据
    }
  }
  return mergeTinyChunks(chunks, opts.minChars ?? 80) // 太碎的块并入邻居
}
```

### T3 · 滑窗与元数据（15min）

滑窗按**段落边界**滑动（遇 `\n\n` 切），而不是暴力字符下标——句子完整性优先于填满窗口。每个 chunk 记录原文偏移 `startOffset/endOffset`：这是 D4 引用定位、以及未来 Web UI 高亮的物理基础。**offset 必须用切前原文的坐标系**，切完再算就乱了。

### T4 · 完整性测试（10min）

```ts
// chunker.test.ts（用 tsx 直接跑的极简断言即可）
const chunks = chunkMarkdown(sampleMd, 'sample.md')
const joined = chunks.map(c => c.content).join('')
const original = stripHeadings(sampleMd)
// 宽松断言：原文每个 20 字滑窗的片段都能在拼接结果中找到（容忍 overlap 重叠）
```

**决策点**：切块器是最值得写测试的模块——它是纯函数、错误会静默扩散（丢一段文字，检索永远命不中那一段，且没人报错）。**「静默失败」的模块必须有测试**。

## 关键决策与原理

1. **混合策略**：纯滑窗实现简单但把「一个完整主题」拦腰斩断；纯语义切分依赖模型/规则成本高。**标题定边界 + 滑窗兜底 + 碎块合并**是工程折中的标准答案；
2. **元数据在切块时采集**：source/heading/offset 是切块器的副产品，却是引用溯源与 UI 高亮的主原料——切块时偷懒不记，后面要重切一遍；
3. **参数化而非写死**：`maxChunkChars/overlap` 做成参数，因为 D5 评测会回来调它们——**今天留的旋钮，就是明天调优的抓手**；
4. **中文特有坑**：没有空格分词，滑窗若按句子切要用 `。！？；` 标点边界，别照搬英文的 sentence tokenizer。

## 自测题（答完翻底部）

1. 块太大和太小各自的具体害处？
2. 为什么滑窗要按段落边界而不是固定字符数切？
3. `startOffset/endOffset` 为什么必须在切前坐标系里记录？
4. 哪类模块最值得写测试？本例的判断依据是什么？
5. 中文文本切块和英文相比要额外注意什么？

---

## 答案与解析

1. 太大：向量语义稀释、命中后挤占生成上下文预算、定位不精准；太小：语义破碎（代词/上下文丢失）、块数暴涨（存储与检索成本升）；
2. 段落是天然语义单元，边界切分保证块内句子完整；固定字符切会把句子拦腰斩断，两侧块都不可独立理解；
3. offset 的消费者是「原文高亮/引用跳转」，它们锚定的是原始文档；切后再算需要反向拼接推断，复杂且易错；
4. 纯函数 + 静默失败 + 下游高价值依赖——三者齐备的模块测试 ROI 最高；切块器三项全中；
5. 分词：中文无空格边界，需按标点切句；且同样字符数下中文信息密度约为英文 1.5~2 倍，块长经验值不能照搬英文的 token 结论。
