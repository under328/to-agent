## 任务卡

### T1 · 一页纸产品定义（20min，想清楚比写代码重要）

```markdown
# AI Notes · 产品定义 v1
## 为谁做
我自己（用户=开发者：反馈回路零成本，需求即真实需求）
## 核心动词（每个动词 = 一个功能边界）
1. 收录：3 秒内把一条信息存进来（粘贴/剪藏）
2. 整理：存完自动打标 + 一句话摘要，不需要我动手
3. 关联：看一条笔记时，相关的笔记自动浮出来
4. 问答：对着我的全部笔记提问（W6 接入）
## v1 明确不做
多用户/登录、移动 App、富文本编辑器、公开分享、云同步
```

**决策点**：「给自己做」不是格局小，是**方法论**——独立开发死于「为假想的用户做功能」，而自己是零成本、说真话的用户。四个动词就是四周的开发主线，超出动词的功能一概不做。

### T2 · 数据模型（20min）

```ts
// 核心表（SQLite）
notes:      id, title, url?, content, tags_json,     // v1 tags 用 JSON 列
            summary?, embed_status, created_at
// 向量与全文：复用 knowledge 内核的模式
note_vecs:  rowid ←→ notes.id, embedding float[2048]
notes_fts:  FTS5(trigram) ← title + content
```

**决策点：tags 用 JSON 列还是关联表？** 标准答案是「按查询模式定」：需要「按标签聚合统计、多标签交集查询」→ 关联表；v1 只有「展示笔记的标签 + 按单标签过滤」→ JSON 列足够，且省两张表的 join 复杂度。**写进注释的迁移条件**：当出现「多标签交集查询」需求时迁关联表。这个「决策 + 反悔条件」的写法，就是轻量级架构文档。

### T4 · 与 docqa 的本质区别（想明白，写进 product.md）

docqa 是「检索已有资料」的工具；ai-notes 是「持续生长的个人知识库」——区别在**写路径**：docqa 的资料基本不变，ai-notes 每天都在增量写入、增量整理、增量关联。这意味着：整理管线（D3）、增量向量化（D4）才是这个产品的技术主线，检索只是早已解决的子问题。

## 关键决策与原理

1. **v1 不做清单 ≥ 功能清单**：独立开发的第一死因是范围失控；「不做清单」是每天对抗范围蔓延的契约；
2. **数据模型的最小化**：三表起步（notes/向量/全文），宁可后期迁移（有明确迁移条件）不要前期过度设计——单用户 SQLite 下迁移成本极低；
3. **复用是结构性的**：knowledge 内核（切块/检索/评测）、成本日志、流式 reader 全部直接复用——前四周的每一个「当时嫌麻烦也做了」的模块，本周都在回报你；
4. **产品定义里写用户场景**：不做「AI 笔记市场分析」，只写「我周三开会时想 3 秒存一条结论，周五写周报想搜出来」——具体场景比抽象定位更能指导功能取舍。

4. 「不做清单」对抗的是什么风险？
5. 为什么产品定义要写具体场景而不是市场定位？

---

## 答案与解析

1. 用户与开发者重合：反馈零延迟零成本、需求绝对真实、且最能坚持（狗粮吃得下去）——独立产品验证期最可靠的形态；
2. 依据是查询模式：仅需展示与单标签过滤时 JSON 列足够简单；迁移条件=出现多标签交集/聚合统计需求，且写进代码注释；
3. docqa 读多写少（资料静态），ai-notes 写密集（每日增量录入）——整理管线与增量向量化是主线，检索是已解决的子问题；
4. 范围失控（scope creep）：独立开发者的时间预算下，每多一个「顺手做了」的功能，核心动词就晚一周被验证；
5. 具体场景能直接推导功能优先级与验收标准（「3 秒存进来」就是性能指标），市场定位不能——它解释不了任何一个按钮该不该存在。
