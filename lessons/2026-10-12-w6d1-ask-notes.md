## 任务卡

### T1 · 检索粒度决策（15min，今天的核心判断）

**问题**：W3 的检索单元是「文档切块」，笔记该用什么粒度？

- **短笔记（≤ maxChunkChars）整条为一个单元**：笔记天然语义完整（一条记录一个想法），切块反而破坏它；
- **长笔记（超长粘贴/剪藏全文）才切块**，但每个 chunk 必须挂 `note_id`——检索命中 chunk 后回溯到笔记。

**引用单位为什么是笔记而不是 chunk**：用户的心智模型是「哪条笔记说的」，不是「哪一段说的」——段内定位（offset 高亮）是详情页的事（明天做）。**检索的对内粒度与对外的引用单位可以不一致**，这是很多 RAG 实现没想清楚的一层。

### T2 · 数据源适配（20min）

```ts
// ai-notes 侧的适配：不改动 knowledge 内核，业务侧组装
export async function searchNotes(query: string, k = 5) {
  const hits = await hybridSearch(query, { k })       // 内核：向量+FTS+RRF（W4-D1）
  return attachNoteMeta(hits)                          // chunk/note_id → 笔记元数据
}
```

**决策点（改造内核 vs 业务侧适配）**：knowledge 内核保持「表无关」的通用能力（向量化/RRF/评测），表结构差异由业务侧适配——内核是引擎，ai-notes 是整车。判据：改动是否让内核「知道了业务」。**内核一旦沾业务，第二消费者（未来别的项目）就废了**。

## 关键决策与原理

1. **粒度分层是常态**：检索单元（chunk/note）≠ 引用单位（note）≠ 展示定位（offset 高亮）——三层各司其职，混为一谈会导致「引用了一堆碎片，用户不知道出自哪条笔记」；
2. **引擎/整车分离**：knowledge 的通用性是它被复用的前提，业务概念（笔记、标签）只在 ai-notes 侧出现；
3. **真实问题驱动评测**：狗粮日志是从「使用」流向「工程」的第一条数据管道——今天不建这条管道，产品就会漂向「技术自嗨」；
4. **拒答照常生效**：笔记库里没有的问题（比如问时事），照旧「笔记中未找到」——私有语料的边界感是这类产品的诚信底线。

## 自测题（答完翻底部）

1. 为什么短笔记整条检索而不切块？
2. 「检索单元、引用单位、展示定位」三层分别是什么？为什么必须分层？
3. 「内核不沾业务」的判据是什么？
4. 引用单位用笔记而非 chunk，对用户意味着什么？
5. 狗粮日志在今天的工程流程里扮演什么角色？

---

## 答案与解析

1. 笔记是天然语义单元（一条=一个完整想法），切块破坏语义完整性；切块的价值只在超长内容的粒度管理——工具服务于内容形态，不是反过来；
2. 检索单元=系统内部找东西的粒度（chunk/note）；引用单位=对用户呈现的出处（笔记）；展示定位=详情页内的片段高亮（offset）。三层分开才能既检索得准又说人话；
3. 看改动是否让内核需要理解业务概念（笔记/标签/用户）——一旦需要，内核就失去了被下一个项目复用的可能；
4. 用户核对出处的心智是「翻到那条笔记」，chunk 级引用会给出大量碎片链接，认知负担大且「来源」的可信体感来自笔记整体；
5. 它是真实需求的入口：真实疑问→首批查询→评测用例→开发优先级，这条管道让产品被使用数据而不是想象驱动。
