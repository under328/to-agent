# W2-D5 ｜ 第 1 篇文章定稿与发布：把过程变成影响力

> **前置**：D1~D4 验收，作品 1 已达「可公开」状态。
> **今日一句话**：文章不是「宣传产品」，而是把你的工程决策公开化——它就是简历的第 1.5 页。

## 今日验收

- [ ] 文章终稿完成：2500~3500 字，含至少 3 张图（架构图/schema 截图/评测分数表）
- [ ] 标题三选一确定，发布到掘金（标签：前端 + AI + 工程化）
- [ ] 文内附：在线 demo 链接 + GitHub 仓库链接
- [ ] 发布后：把链接发到朋友圈/1~2 个技术群；所有评论 24h 内回复

## 任务卡

### T1 · 结构定稿（对照大纲填充，10min 核对）

```
1. 痛点故事：每周五花 1 小时拼周报（共鸣开场，40 字内进入正题）
2. 方案：为什么是「结构化输出」而不是「让 AI 写作文」
3. schema 设计：枚举/optional/describe 三个反幻觉细节
4. tool calling 取舍：大部分场景用确定性函数（本篇最大差异化观点）
5. 评测：20 例回归集 + judge 双轨，放真实分数表
6. 成本账：路由+缓存后每篇周报成本 ¥0.0x（放 D3 的表格）
7. 踩坑：至少 2 个（真实感来自失败细节，如缓存不升版本的坑）
8. 局限与下一步（空周/隐私/多语言——诚实反而加分）
```

**写作红线**：不放没跑过的数据、不吹「革命性」、每 个观点都能在仓库里找到对应 commit。

### T2 · 标题与封面（10min）

标题公式三选一方向：①数字+结果：《2 个周末、20 个评测用例：我把 AI 周报生成器做成了真的》；②反差+观点：《做 AI 周报工具时，我 80% 的 tool calling 都删掉了》；③教程+完整：《从 0 到上线：前端工程师的 AI 应用工程化实录》。

### T3 · 发布与冷启动（15min）

- 发布时间：工作日早 9 点前后或晚 8 点前后（掘金流量高峰）；
- 冷启动：朋友圈 + 2 个技术群 + V2EX「分享创造」节点（各配一句不同人设的推荐语，勿复制粘贴同一段）；
- 评论区 24h 内回复：每条尖锐评论都是下一篇文章的选题。

## 关键决策与原理

1. **文章的主叙事是「决策」而非「功能」**：读者能学到东西（schema 反幻觉、tool 取舍、评测方法），文章才有转发价值——功能介绍谁都能写，决策过程才是你的护城河；
2. **放真实失败**：「缓存没升版本导致新旧结果混合」这类坑比成功案例更建立信任，也最容易被面试官追问出深度；
3. **一鱼五吃**：这一篇文章的素材同时供给——GitHub README 的工程亮点、简历项目描述、面试自述、后续文章、内推时的自我介绍。写一次，五个场景复用；
4. **发布只是开始**：24h 互动期决定掘金推荐量；尖锐评论里藏着产品的真实需求（记录进 journal，W10 用户访谈的预演）。

## 自测题（答完翻底部）

1. 为什么技术文章的主叙事应该是「决策」而不是「功能」？
2. 「放真实踩坑」建立信任的机制是什么？
3. 「一鱼五吃」具体指哪五个复用场景？
4. 冷启动为什么要对不同渠道写不同推荐语？
5. 尖锐的负面评论的正确处理姿势是什么？

---

## 答案与解析

1. 功能谁都能实现，读者无法从功能介绍里带走可复用的东西；决策过程（为什么这么做、放弃了什么）才有知识增量，才值得转发和引用；
2. 只讲成功像营销，失败细节证明「真做过且复盘过」；且踩坑内容往往是同行最实用的避坑信息，专业读者据此判断作者水平；
3. GitHub README、简历项目描述、面试项目自述、系列文章素材、内推/社交场合的项目介绍——同一套素材一次生产多处复用；
4. 各渠道语境与人设预期不同（朋友看故事、技术群看干货、V2EX 看创造过程），复制粘贴同一段会被识别为营销，转化率反而低；
5. 24h 内认真回复（不对抗、先感谢）；评论指出的问题验证后修复并@对方——把批评者变成关注者，同时收获迭代素材。
