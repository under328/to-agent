# W6-D4 ｜ 批量处理与健壮性：启动续跑、防抖与重试

> **前置**：D1~D3 完成。
> **今日一句话**：单用户的系统也要有「生产级韧性」——但用最轻的手段：扫表续跑，而不是重型队列。

## 今日验收

- [ ] 启动续跑：服务启动时扫描 pending 超时/中断的整理任务并自动续跑（解决 fire-and-forget 重启丢任务）
- [ ] 录入防抖：3 秒内连续录入合并为一个整理批次（一次 LLM 调用整理多条）
- [ ] 整理失败自动重试 1 次（间隔 30s），仍失败转 failed 等手动
- [ ] 批量导入：粘贴多段（`---` 分隔）一次录入多条，带进度反馈

## 任务卡

### T1 · 启动续跑（15min，今天的方法论核心）

```ts
// 服务启动时（instrumentation.ts / 入口最前）：
export async function recoverPendingTasks() {
  const stuck = getNotes({ embed_status: 'pending', updatedBefore: minutesAgo(5) })
  console.log(`[recover] 发现 ${stuck.length} 条未完成整理，重新入队`)
  for (const n of stuck) setTimeout(() => enrichNote(n.id).catch(console.error), 0)
}
```

**决策点（为什么扫表就够了）**：队列系统的本质是「**待办状态的可靠记录 + 断点重放**」。状态已经持久化在 notes 表（W5-D3 的 embed_status），启动时扫一遍表重放，就获得了队列 90% 的价值——而成本是 15 行代码。真队列（BullMQ/Redis）的附加价值在**多消费者、延迟敏感、跨机分布式**——单机自用产品一条都不占。**升级条件**：任务量到了秒级堆积、或需要不同 worker 消费不同任务类型时。

### T2 · 录入防抖与批次整理（15min）

```ts
// 3 秒内的连续录入 → 同一 batch_id；整理器按批次取货
async function enrichBatch(batchId: string) {
  const notes = getNotesByBatch(batchId)
  const { object } = await generateObject({
    model: flash, temperature: 0,
    schema: z.object({ items: z.array(z.object({ id: z.number(), tags: z.array(z.string()).max(3), summary: z.string() })) }),
    prompt: `现有标签：${listTags()}\n\n逐条整理以下笔记（id 标注在每条前）：\n${notes.map(n => `[id=${n.id}] ${n.content.slice(0, 600)}`).join('\n---\n')}`,
  })
  // 逐条落库：批次内某条失败不影响其他（部分成功语义）
}
```

**决策点（合批的取舍）**：10 条笔记合 1 次调用 ≈ 省 60~70% 的固定开销（系统词/现有标签表重复）；代价是单条失败影响面变大、prompt 变长。用「逐条落状态」化解：解析结果按 id 各自更新，谁失败谁标 failed。**合批省钱，状态细粒度保命**。

### T3 · 自动重试（5min）

整理失败 → 30s 后自动重试 1 次 → 再失败转 `failed`（手动按钮）。上限必须存在：无上限重试 × 系统性故障（如 Key 过期）= 无限烧钱循环。

### T4 · 批量导入（10min）

粘贴框支持 `---` 分隔的多段 → 拆分为多条笔记逐条走录入管道，UI 显示「3/7 条已入库」。会议记录、课程笔记的搬运场景一次搞定——这也是把「旧笔记资产」迁进来的必经之路。

## 关键决策与原理

1. **队列的本质是状态 + 重放**：想清楚这一点，90% 的「要不要上队列」问题都有了廉价答案——先把状态写可靠（你有 embed_status），重放只是时间问题；
2. **合批经济学**：LLM 调用的固定开销（系统提示/标签表/建连）摊到多条上，是「批量」最实在的收益；而部分成功语义（逐条落状态）是合批不出事故的前提；
3. **重试必须有上限**：无上限重试在系统性故障下等于自动烧钱，重试是「对瞬时故障的礼貌」，不是「对持久故障的倔强」；
4. **批量导入是用户资产迁移的桥**：自用产品能否「活下来」取决于旧数据能不能无痛搬进来——这条管道同时服务于「当时的一次性迁移」和「日常的会议记录搬运」。

## 进阶挑战（选做）

- 续跑任务加简单并发限制（同时最多 2 条在整理，防 LLM 限流）；
- 批量导入支持「自动识别分隔」：按空行 + 字数启发式切段，连 `---` 都不用打。

---

## 答案与解析

1. 可靠的状态记录 + 断点重放。扫表续跑两者都有（状态在 embed_status、重放在启动扫描），缺的是多消费者/低延迟/分布式——单机场景用不到；
2. 固定开销摊薄（系统词/标签表/调用次数）；合批把多条绑进一次调用，若整批原子处理则一损俱损——逐条落状态让失败被隔离在单条粒度；
3. 系统性故障（Key 失效/欠费/平台故障）下的无限烧钱循环——重试针对瞬时抖动，不针对持久故障；
4. 日常场景：会议记录一次倒多条；迁移场景：把历史笔记资产搬进系统——同一个管道，两种动机；
5. 任务量堆积到秒级、需要不同 worker 消费不同任务类型、跨机分布式部署——三个条件任何一个出现再上，否则扫表就是正解。
